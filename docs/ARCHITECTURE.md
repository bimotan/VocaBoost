# VocaBoost Architecture

## Layers

- `app`: JavaFX startup and dependency wiring. `AppServices` opens one database and wires its repositories and services; the app and the UI tests both build the window through it.
- `ui`: Programmatic JavaFX (no FXML). `MainWindow` is a thin shell that builds the `DeckHeader` and one view class per tab (`dashboard`, `decks`, `review`, `importing`, `stats`, `words`, `settings` subpackages) on a shared `ViewContext`:
  - `DeckContext` holds the current deck and the active deck list and remembers `ui.lastDeckId`; a rename is not a deck switch.
  - Views never refresh each other. Whoever changes data publishes a `DataChange` (`WORDS`, `REVIEWS`, `DECKS`, `SETTINGS`, `REVIEW_SETTINGS`, `GOALS`) on `DataChanges`; Dashboard, Decks, Word List and Statistics use `LazyRefresh`, so a change only marks a hidden tab stale and it is recomputed when shown (Statistics on every visit, since it depends on the clock).
  - `UiAsync` runs slow work on `vocaboost-background-task` threads. Callers capture the deck, card or request the work is for before starting it, and pass trigger buttons that stay disabled while it runs; `LatestRequest` tickets drop results that arrive for something no longer shown.
  - The Review tab's flow lives in `ReviewSessionPresenter`, which has no JavaFX dependency (states `IDLE`, `AWAITING_ANSWER`, `ANSWERED`, `SAVING`, `RATING_FAILED`, `COMPLETE`); `ReviewView` only renders it and adds the keyboard shortcuts (Enter submits, then 1-4 or Space rate).
  - `UiErrors` logs and shows failures; every modal dialog and file chooser goes through the `Dialogs` interface (`JavaFxDialogs` in the app, a scripted fake in the UI tests), and key controls have stable ids (`node.setId`) that the UI tests look up.
- `service`: Review scheduling, goals, achievements, dictionary lookup, import/export, backup, validation, and analytics.
- `repository`: SQLite schema initialization, migration, and CRUD.
- `domain`: Records and entities such as `WordCard`, `Deck`, `ReviewLog`, goals, achievements, dictionary entries, and statistics rows.

Business logic stays out of JavaFX controls and does not use `Scanner`, `System.out`, or `System.exit`.

## Build, CI and Packaging

- The Maven Wrapper (`./mvnw`, `mvnw.cmd`) downloads a pinned, checksum-verified Maven; only a JDK 17+ is needed. The code compiles with `--release 17`, so APIs newer than Java 17 are rejected even on a newer JDK. Every plugin version is pinned in `pluginManagement`, and the enforcer checks the Java and Maven versions, pinned plugins, converging dependency versions and duplicate classes.
- `./mvnw test` skips the JavaFX UI tests (tag `ui`); `-Pui-tests` runs them too (under `xvfb-run` on Linux). Each test run writes a JaCoCo report to `target/site/jacoco`; `verify` fails when the service and repository code together drop below 60% line coverage. `-Pscreenshots` retakes `docs/screenshots` from the real window (`DocsScreenshotsUiTest`). The tests do not depend on the wall clock: the services take a `Clock` (`AppServices.Builder.clock`, which also dates new decks and words), tests that depend on dates give them fixed clocks, and the UI test harness opens the window on a `TestClock` that stands at 10:00 on 10 March 2026, far from midnight and the 4 am day rollover, until a test moves it. So they give the same results in any time zone and at any hour, also when a run crosses midnight or 4 am.
- `package` builds a jar with a `Main-Class` and a `lib/` class path and copies the runtime jars to `target/lib`, so `java -jar target/vocab-trainer-<version>.jar` starts the app. The jar is platform-neutral; the JavaFX jars carry natives for one platform, which the openjfx POM picks from the build OS. `-Djavafx.platform=win|linux|mac|mac-aarch64` resolves another platform's jars instead. JavaFX runs from the class path through `VocabTrainerLauncher`, which JavaFX logs as an unsupported configuration but which works.
- `scripts/package-windows.ps1` (Windows; `-PackageType exe|msi` needs WiX, `-Console` adds a console window) and `scripts/package.sh` (Linux and macOS) build with the wrapper, read the version from the jar build's `pom.properties`, and stop with a non-zero exit when a step fails. jpackage can only package for the OS it runs on. The bundled runtime is made by jlink from the modules jdeps finds plus `jdk.crypto.ec` (HTTPS), `jdk.charsets` (GBK/GB18030) and `jdk.localedata` (en and zh only), without debug info, man pages, headers or commands: an 80 MB app image instead of 180 MB. Both give jpackage the app icon, a V with a spark on a rounded square: `packaging/icons/vocaboost.ico` on Windows, `vocaboost.icns` on macOS and the 512 px PNG on Linux. `packaging/icons/make-icons.sh` renders them from `vocaboost.svg`, with the window icons in `src/main/resources/icons` (16 to 512 px) that `VocabTrainerApp` puts on the stage. Started with `--smoke-test` (`SmokeTest`), the app opens a new database in a temporary folder, with `user.home` pointed there before anything reads it, so the user's data is never opened; it waits until the main window is shown, has stayed free of errors and dialogs for 2 seconds and has finished its background work, then exits with 0, or prints why not (a startup exception, an uncaught exception, a SEVERE log record, a dialog, a missing window icon, or no window within 120 seconds) and exits with 1. `scripts/smoke-test.sh` (Linux, macOS) and `scripts/smoke-test.ps1` (Windows) run a packaged launcher with it and fail on a non-zero exit or a timeout.
- CI (`.github/workflows/maven-test.yml`) runs `verify` on Windows and Linux with JDK 17 and 21, all tests including the UI tests under xvfb in a time zone where it is 1 am, between midnight and the study-day rollover (uploading the UI snapshots and coverage report), and both packaging scripts, smoke-testing the Windows and Linux app images. Pushing a tag `v<pom version>` runs `release.yml`, which tests, packages and smoke-tests the Windows app image and attaches it as a zip with its SHA-256 to the tag's GitHub release. Dependabot proposes Maven and Actions updates weekly, keeping JavaFX on 21 LTS and JUnit on 5.

## Settings

The Settings tab (`ui/settings/SettingsView`) holds the configuration: the Add / Import tab only adds, looks up, imports and exports words, and the Statistics tab only shows charts and exports. Every setting is saved in the `settings` table as soon as it is changed and applies at once; none needs a restart.

- **Study** (`StudySettingsBox`). The desired retention is a slider from 80% to 97% in steps of 1%, saved when the thumb is let go (or at once with the keys). Its hint states the trade-off, higher = more reviews, and the interval a retention gives where 90% gives 10 days (95%: 5 days, 80%: 24 days). The study day starts at an hour from 00:00 to 23:00. `SchedulingSettings` saves both (`scheduler.desiredRetention`, `scheduler.dayRolloverHour`) and hands the new options to the running scheduler (`ReviewScheduler.setOptions`): the next rating and interval preview use them, the Review tab previews an answered card again, and due dates already set stay. `ReviewService`, `GoalService`, `StatsService` and the Word List read the scheduler's study day at every call, so after a new rollover hour "Due today", the deck table, the Word List's status, the daily goals and the day a review counts for follow it on their next refresh (`REVIEW_SETTINGS` marks them stale). A retention saved below 80% (by hand or an older version) is shown as it is.
- **New words per day.** The new-cards-per-day limit of every deck without a limit of its own (`review.newCardsPerDay`, 20 until changed). The Review tab's "New words/day" sets the current deck's own limit (`review.newCardsPerDay.<deckId>`), which the default then no longer changes; the hint names the current deck's own limit when it has one, and "Use the default for this deck" drops it (`ReviewSettings.clearNewCardsPerDay`), so the deck follows the default again.
- **Daily goals.** A summary of the default goals, a deck's own and the session size, and "Edit goals", the Dashboard's form (`GoalsDialog.open`).
- **Exam.** The current deck's exam (countdown, date, and whether it is every deck's or the deck's own) with its new-word plan, and "Set exam date", the Dashboard's form (`ExamDialog.open`); see Exam Planning. The row is read again each time the Settings tab is shown, so its plan follows the ratings and imports made on other tabs and its countdown the clock. A limit the Dashboard's plan set is the deck's own limit, so the New words per day hint names it and "Use the default for this deck" drops it.
- **Offline mode.** The header's switch and the Settings tab's are one setting: `OfflineMode` keeps both check boxes on the saved value, publishes `SETTINGS` and puts both back when saving fails.
- **ECDICT and AI.** The ECDICT box and the AI provider box (with Test, Clear AI cache and the API key controls) moved here from Add / Import with their control ids; Regenerate stays on the Review tab with the explanation it replaces.
- **Data and Logs.** "Open data folder", "Open log folder" (moved from Statistics; the Dashboard keeps its "Open data folder") and "Open snapshots folder" (created when there is no snapshot yet) open the folders without showing their paths, which name the user's account. A note says how to go back to a snapshot (see Snapshots).
- **Display.** The text size of the window and its dialogs: 100% (the system's), 115% or 130% (`DisplaySettings`, `ui.textSize`); see Window, Style and Accessibility.
- **Language.** A disabled placeholder (English) for the translation of the app.

A setting that cannot be saved is reported and its control goes back to the value in effect.

## SQLite Schema

- `decks`: active/archived vocabulary collections. Names are unique among active decks only, ignoring upper and lower case (a partial unique index on `name COLLATE NOCASE`, which folds the letters A to Z: "GRE" and "gre" are one name), so an archived deck's name can be reused; restoring an archived deck is refused while an active deck has its name in any case, and the messages name both spellings when they differ. A deck can be renamed to its own name in other case. At least one deck always stays active. Startup opens the last used deck, falling back to the oldest active deck, and never looks a deck up by name, so the default deck can be renamed or archived.
- `words`: deck-scoped cards, metadata, tags, archive flag and FSRS card state (`card_state`, `stability`, `difficulty`, `learning_step`, with `next_review_at` as the due time, `last_reviewed_at`, `repetitions` and `lapses`). The SM-2 columns of older versions (`easiness_factor`, `interval_days`, `consecutive_correct`) are kept and still written; see Review Algorithm.
- `review_logs`: typed answers, correct answers, similarity, the rating the user chose (`rating`), the rating the schedule used (`effective_rating`: the chosen one capped by the answer check unless the user overrode it) and whether the user's override of the check made that rating count (`overridden`), response time, what the review was (`kind`: `LEARN` for the first review of a new card, `REVIEW`, or `PRACTICE` for a Weak Words practice of a card that was not due) and the question direction (`direction`: `EN_TO_ZH`, `ZH_TO_EN` or `CLOZE`; the column has no constraint, so `CLOZE` needed no migration, and a version that does not know a direction reads it as unknown). Logs written before schema version 6, or by an older version since, read as `REVIEW` with no direction; logs written before version 7 have no effective rating and read as their rating capped by their similarity, which is how those versions scheduled them. Indexed by `(word_id, reviewed_at, rating)`, which identifies one review (unique, so a restored backup never adds a review twice), and by `reviewed_at`. JSON backups carry `kind`, `direction`, `effectiveRating` and `overridden`, and "Export review logs CSV" has them as its last columns (`effective_rating` is what the review counted as, also for a log written before version 7).
- `daily_goals`: one row per deck and study day that had a review or earned XP: the goals in effect that day, the XP earned and whether the daily goal was completed. Its review, correct and new-word counters are still written, in the rating's transaction, for older versions and backups, but nothing reads them: the day's numbers come from `review_logs` (see Goals, XP and Streak). Reading progress never writes; a day without a row has the current goals and no XP.
- `achievements`: unlocked badges. Review-count, daily-goal and overdue badges belong to a deck; streak badges belong to no deck (`deck_id` 0).
- `dictionary_cache`: cached lookup payloads by English word.
- `settings`: local configuration such as saved ECDICT CSV path and load metadata, the last used deck (`ui.lastDeckId`), and whether the bundled starter words were already imported (`starter.imported`).
- `ai_cache`: cached AI explanations from the configured provider, keyed by word plus a hash of the endpoint, model, prompt version, word fields and the learner's answer (see AI / Mock Design). The upgrade to schema version 1 deletes rows that hold the mock fallback text, which older versions cached by mistake.

The schema is versioned with `PRAGMA user_version` and upgraded by `SchemaMigrations` when `DatabaseManager.initialize()` runs. Version 0 is any database from before versioning: step 1 repeats what those releases did on every start (idempotent `CREATE`/`ALTER` steps, the deck-scope rebuild of `daily_goals` and `achievements`) and merges back rows that an interrupted rebuild left in `daily_goals_old` / `achievements_old`. Later steps rebuild `decks` without the old column-level `UNIQUE` (foreign keys off, same ids, `foreign_key_check` afterwards), collapse duplicate review logs, add indexes, add the FSRS columns (version 5), the review log kind and direction with the review-queue index `idx_words_queue` on active words (version 6), the review log's effective rating and override flag (version 7) and active deck names unique ignoring case (version 8: of active decks whose names differ only in case, the oldest keeps its name and each newer one gets " (2)", " (3)", ..., the first such name no active deck has, and each rename is logged). Each step runs in one transaction together with its version bump, so an interrupted upgrade is retried on the next start; a new database goes through the same steps. Before the first step that upgrades an existing database (one of an earlier version, or from before versioning), a snapshot of it is written (see Snapshots). Existing local databases are never deleted.

`DatabaseManager` pools connections: `getConnection()` lends one out and closing it returns it (statements the borrower left open are closed, a connection that cannot be reset is discarded). Each connection is set up once with `foreign_keys=ON`, `busy_timeout=5000` and `synchronous=NORMAL`, and the database uses `journal_mode=WAL`, so the UI can read while a background task writes. `VocabTrainerApp.stop()` closes the pool; tests close every database through the `TestDatabases` extension, which also fails a test that leaks a connection. Services do not run SQL themselves; queries live in the repositories.

Multi-step writes use `DatabaseManager.inTransaction` (exposed to services as `TransactionRunner`). It binds one pooled connection to the calling thread; repository calls made inside the work, and nested `inTransaction` calls, join that transaction, and closing the joined connection is a no-op. The transaction commits only if all the work succeeds. Rating a card (schedule, review log, goal progress, achievements and their XP), bulk word imports and backup restores are atomic.

- **Writers wait in line.** An outermost transaction takes a fair lock (`ReentrantLock(true)`) before its `BEGIN IMMEDIATE`, waiting at most the busy timeout, so transactions of the app start in the order they asked. SQLite's own wait for its write lock retries at growing intervals, and a thread writing short transactions back to back could keep winning it (`TransactionTest` starves a transaction for the whole busy timeout without the lock).
- **Long writes.** Background work never holds the write lock for long where the user may write meanwhile. Building a deck from an ECDICT tag writes batches of 250 words, each in its own short transaction with a 10 ms pause after it (for single statements, which do not wait in line), so a rating waits for one batch at most. A JSON backup restore stays one transaction, to be all or nothing; while it runs, the window pauses what would wait for it: `LongWrites` (on the `ViewContext`) carries the note "A backup is being restored...", the Review tab shows it and disables rating (buttons and keys), Already known, Suspend, Undo, Regenerate and the session settings (an answer can still be typed and checked), and the header's deck selector and deck buttons are disabled; everything comes back when the restore ends, failed or not. The backup export and restore buttons are disabled while either runs.

### JSON Backups

"Export JSON backup" (Statistics tab) writes the current deck: every word with its whole schedule and suspension, its review logs, goal days and badges (format version 2, read by `BackupService` with Jackson; version 1 files of older versions still restore). "Import JSON backup" asks what to do and restores in one transaction, after a snapshot (see Snapshots):

- **Keep current progress** (the default) or **Use backup progress** restore into the current deck. A word the deck lacks is added with the backup's schedule. A word the deck has keeps its schedule, or with Use backup progress takes the backup's; the word's text stays the deck's. A word the deck has but never reviewed (`NEW`, no repetitions, no review logs) has no progress to keep: the backup's card replaces its schedule and suspension under either choice, unless the backup never reviewed or suspended it either. So restoring a backup after a reinstall, whose 215 starter words are the backup's words never reviewed, brings back their progress.
- **Restore into a new deck** creates a deck named as the backup's deck (a version 1 backup names none: the file does), with " (2)", " (3)", ... when an active deck has that name in any case, in the restore's transaction; every word is new there. The window then switches to it.
- **Review logs follow the schedule.** A word's logs are restored only when its schedule is the backup's afterwards: it was added, its schedule was replaced, or it already had it (restoring into the deck the backup came from). The logs of a word that keeps its own, different progress are not added, so they cannot inflate that card's history; the summary counts them. A log with the same word, time and rating as one already there is the same review and is skipped (the unique index).
- A restore earns no XP and counts no new words; goal days and badges the database lacks are added. Rows the file gets wrong are skipped and listed in the summary and the log.

### Snapshots

`DatabaseSnapshots` (repository) writes safety copies of `vocab.db` with SQLite's `VACUUM INTO` into `snapshots` next to it: a consistent, compacted copy of the whole database, also while other connections write, in one file without the write-ahead log. One is written before a schema upgrade of an existing database (`vocab-<date>-<time>-before-upgrade-v8.db`, by `DatabaseManager.initialize`), one before each JSON backup restore (`-before-restore`, in the restore's background task) and one a day at startup (`-daily`, by `AppServices`, unless a snapshot was written that day or the database was just created). The newest 10 are kept, ordered by when they were written (the file time, which a change of time zone does not move), and the snapshot just written is never the one deleted; only files named like a snapshot are deleted. A snapshot that cannot be written (a full disk, a file in the folder's place) is logged and stops nothing: not the start, the upgrade or the restore.

Going back to a snapshot is done by hand while the app is closed, as the note in Settings → Data and Logs says: delete `vocab.db-wal` and `vocab.db-shm` if they are there (a write-ahead log left by a crash would otherwise be applied to the copied file), copy the snapshot over `vocab.db` and start the app again. Decision: there is no "Restore snapshot..." button. Replacing the database file under the running app's pooled connections and open views is not safe, and doing it at the next start would need a restart flow; the manual steps are short and make clear that everything since the snapshot is lost.

### Timestamps

Decision: times are stored as the computer's local wall-clock time without a zone (`DateTimeUtil.toDatabase`, ISO `yyyy-MM-ddTHH:mm:ss[.nnn]`), and days (`daily_goals.goal_date`, the study day of a review) as local dates; they are compared as text in SQL. They are not migrated to UTC instants. VocaBoost is a single-user app on one computer, and its study days are meant to follow the clock on the wall: "due today", the new-word allowance, the daily goal and the streak change at the rollover hour of the user's local time wherever they are, which a zone-less local time gives directly and a UTC instant would only give after converting every comparison with the current zone. Converting every time column would be a large migration of every table for a rare case.

What happens when the local time changes:

- **Moving to another time zone** (say from Beijing to New York, 12 or 13 hours back) shifts every stored time by that much relative to real time. Due times stay the same wall-clock times: a card due tomorrow at 4:00 is due at 4:00 New York time, and a learning step due in 10 minutes waits until its clock time comes round, at most the zone difference later in real time (earlier when moving east). Review intervals count study days, so this costs at most part of a day. A review just after the move can be stored with an earlier time than the last review before it, so logs of that day may sort in a different order; the study day each review counts for is still the local day it was made on. The streak counts study days with a review: the day of the move is one study day of the old or the new zone's clock, so it neither breaks nor doubles unless a whole local day passes without a review.
- **Daylight saving time** repeats or skips one hour of local time once a year. A review in the repeated hour may sort before one made an hour earlier; due times move by at most that hour.
- **The rollover hour** (4:00 by default) limits both: a study day changes at 4:00 local time rather than at midnight, so the hours around a zone change or a daylight saving switch (which happen at night, around 2:00 to 3:00) fall inside one study day, and late-night reviews never land on a different day than the evening's.

Snapshots and JSON backups store the same local times, so restoring one on a computer in another zone shifts it the same way.

## Review Algorithm

Reviews are scheduled with FSRS-5 and its published default parameters. The pure arithmetic is in `service.scheduling`: `Fsrs` (stability, difficulty, retrievability R = (1 + 19/81 · t/S)^-0.5 and the interval for the desired retention), `StudyDay` (the day rollover) and `CardScheduler` (states, steps, intervals and fuzz); `ReviewScheduler` applies them to a word.

- **Grades.** Again, Hard, Good and Easy are grades 1 to 4. The schedule uses the rating the user chose, capped by the answer check (see Answer Checking) unless the user overrides it; each review log keeps both. The rating buttons show the interval each rating would give for the checked answer (`ReviewService.previewRatings`, nothing is written), e.g. "Good (3) · 4d", and when the check caps a rating what it counts as, with the answer similarity: "Good (3) → Hard (53%) · 1d"; after a wrong answer every button shows Again's interval. The suggested rating, the best the answer counts as but at most Good, has the focus, so Space confirms it.
- **States.** A card is `NEW`, `LEARNING`, `REVIEW` or `RELEARNING`. New cards go through learning steps of 1 and 10 minutes (Again restarts them, Hard repeats a step, Good moves on and graduates after the last, Easy graduates at once); a review card rated Again is a lapse and goes through a 10-minute relearning step. Graduating uses the FSRS stability as the interval.
- **Memory.** The first rating sets S and D from the grade. Later reviews use the time actually elapsed in whole study days: a success at low R raises S more than one at high R, so an overdue success grows the interval more than an early review, which barely changes it; a review on the same study day uses FSRS's short-term formula. Intervals aim at the desired retention (0.9), are capped at 36500 days and, from 3 days on, get a fuzz of a few percent derived from the card id and its review count (reproducible, but cards learned together spread out). Hard, Good and Easy always give increasing intervals.
- **Study day.** A study day starts at the rollover hour (4 am). Intervals count study days: a review due in 1 day is due from the start of the next study day, not 24 hours later. A learning card is due at its exact step time; any other card is due today when it is due before the next rollover. The dashboard's "Due today", the deck table and the review session use that rule (`WordCard.isDue`, `WordRepository.countDue`/`countDueByState` and the review queues).
- **Settings.** `scheduler.desiredRetention` (0.7 to 0.97) and `scheduler.dayRolloverHour` (0 to 23) in the `settings` table override the defaults; they are read at startup, invalid values are logged and ignored, and the Settings tab changes them while the app runs (see Settings).
- **Memory, mastered, weak, leeches.** The Word List's Memory column, the memory chart and the selector weights use R now ("New" for a card never reviewed). A word is mastered when it is in review with S of at least 21 days, whatever lapses it had. A word is weak when it is relearning, was rated Again within its last 3 reviews (`repetitions > consecutive_correct` and `consecutive_correct < 3`), or has D of 7 or more and is not mastered; an old lapse alone no longer makes a word weak. Both rules exist as `WordCard` predicates and as SQL with the same thresholds, and `WordPredicateAgreementTest` keeps them in step. A word that lapses 8 times is tagged `leech` (and logged); the Review tab says so, its details show "Leech", and the Word List can filter leeches.
- **Next card.** See Review Sessions: learning steps first, then review cards by lowest R and new cards up to the daily limit, from separate queries. `WordSelector` (weights by 1 - R) only picks among weak words in Weak Words mode.
- **Response time.** `review_logs.elapsed_millis` is the time from showing the card to submitting the answer; the presenter records when the card was shown and counts only the time the Review tab was on screen (the first card is loaded at startup, behind the Dashboard). Logs written by older versions hold the time from submitting to rating.

Schema version 5 adds the FSRS columns; the SM-2 columns stay and are still written (the interval as the scheduled interval, 0 while learning, and the easiness factor read from the difficulty), so an older version can still open the database and older backups still restore. Existing rows get no state (`card_state` NULL), and `CardStateBackfill` derives it at startup, in one transaction: a word with review logs is replayed log by log, with the rating each log counted as (for a log without an effective rating, its rating capped by its similarity) at the logged time and without learning steps (the versions that wrote those logs had none); a word without logs is estimated from its SM-2 schedule (never reviewed: `NEW`; otherwise `REVIEW` with S = the interval, at least half a day, and D from the easiness factor, 2.5 to 5 and 1.3 to 9) and keeps its lapse count, so it is tagged `leech` from 8 lapses like a replayed word. Rows of the legacy text import are estimated the same way. A word an older version adds later is derived the same way on the next start. JSON backups carry the FSRS fields next to the SM-2 ones (format version 2, so older versions still read them); restoring a backup without them derives the state the same way, after its review logs are restored.

## Answer Checking

`AnswerGrader` grades a typed answer in the direction the question was asked; the grade (`AnswerGrade`) is a similarity from 0 to 1, the best rating the answer can count as and a verdict that the Review tab explains under the answer.

- **English to Chinese** (`SimilarityService.calculate`). A gloss is split into meanings at `; ； , ， / 、`, line breaks (also ECDICT's literal `\n`), spaces between Chinese characters and before a part-of-speech marker (also "n.放弃 v.抛弃" and "放弃v.抛弃"), but never inside brackets. Each meaning loses leading part-of-speech markers (`n.`, `vt.`, `adj.`, several in a row, any case), bracket tags (`[网络]`, `【医】`), punctuation and spaces; full-width characters count as half-width, a trailing 的, 地 or 得 is ignored when two characters remain (清晰 is 清晰的, 获得 stays), and a parenthesized part is optional ("(使)减弱" matches 使减弱 and 减弱). The typed answer is split the same way, so several meanings can be typed; the best pair of typed and correct meaning counts. An equal pair scores 1.0, others the mean of character-bigram Dice and Levenshtein similarity. The similarity caps the rating: below 55% Again, below 75% at most Hard, below 90% at most Good.
- **Chinese to English.** The word itself, ignoring case, accents (naive is naïve), spaces and hyphens, counts as anything. Another real word scores 0 and counts as Again however close its spelling: a well-known confusable (affect/effect, principal/principle, proscribe/prescribe, elicit/illicit and a few more) or another active word of the deck, unless that word shares a meaning with the asked gloss: then it is a synonym, counts as right, and the Review tab says so (several starter words share a meaning, and the prompt allows any of them). Otherwise the letters are compared by Damerau-Levenshtein distance d (similarity 1 - d / length): one typo per 5 letters of the word counts at most as Hard ("lucud" for lucid: 80%, Hard), anything further off, or any slip in a word under 5 letters, as Again.
- **Override.** When the check caps the rating, "I was right" (`overrideButton`) lifts the cap for that answer: the rating the user then chooses counts as it is, and the log records `overridden` (only when the override changed what that rating counts as, so "I was right" followed by Again is an ordinary Again). Afterwards the suggested rating has the focus again. The measured similarity is still logged.
- **Correct.** An answer is correct when its review did not count as Again: `ReviewLog.isCorrect()`, and the same rule in SQL (`ReviewLogRepository.CORRECT`, with the similarity cap for logs without an effective rating). Session accuracy, the daily goal's correct count, the dashboard and daily accuracy, the hardest words' Again count and the Markdown report all use it; `CorrectAnswerAgreementTest` keeps the two in step. Achievements do not depend on correctness. Review XP depends on the rating the review counted as.
- **Starter words.** Every bundled starter word has a meaning no other starter word has (`StarterGlossTest`), so a Chinese-to-English prompt points at one word; words that share a meaning accept each other as synonyms.

## Word Details

A word's phonetic, part of speech, example sentence, note and tags are shown in a details card (`WordDetailsCard`, built from the FX-free `WordDetails`), one row each and only the rows that have a value. The example has the word in bold, also an inflected form of it ("The mentor **admonished** him"): `service.cloze.ClozeMaker` finds the word as a whole word, ignoring case, with the forms ECDICT's exchange field lists for it (`LocalDictionaryService.inflections`, so "forwent" for forgo once ECDICT is imported) and the forms simple rules give (`Inflections`: -s, -es, -ed, -d, -ing, -ly, -ies, -ied, -ily, a dropped e, a doubled final consonant, -ic to -icked and -ically); in an expression of several words the first or last word may be inflected.

- **Review tab.** Before the answer is submitted, a line under the question shows only what cannot give the answer away (`ReviewSessionPresenter.hint`): English to Chinese shows the phonetic, the part of speech and the example, unless the example has Chinese in it (a translation would give the meaning away); Chinese to English shows only the part of speech, since the phonetic and the example give the English word away. The note and tags, which often hold the meaning or an English definition, are never shown before. Once the answer is checked, the card under the result shows all of them; it is hidden again for the next card.
- **Word List.** The card under the table shows the selected word, which stays selected (with its new details) after Edit or a refresh. The edit dialog edits the phonetic too.
- **Adding.** The lookup fills the add form's phonetic. When "Add word" finds the word in a dictionary and the form's phonetic is empty, it takes the dictionary's phonetic for that word (`WordVerificationResult.phonetic`): only from an entry for the word itself, never from the base form an inflection was found under.

## Word List and Decks

- **Reading and filtering.** The Word List reads the current deck's words, or every active deck's, once per refresh: after a data change, a deck switch, "All decks" or Refresh. The search box (English, Chinese or tags, ignoring case), the status filter and the tag and part-of-speech filters filter those rows in memory (a `FilteredList` with `WordListFilter`), and the table sorts them (a `SortedList` bound to the table's comparator), so typing never reads the database. A word's status, memory and whether it is due are those of the time the list was read. With 10,000 words a keystroke takes 2 to 60 ms and a sort 25 to 100 ms under xvfb on the test machine (`WordTableUiTest` prints them); before, each pause in typing ran a `LIKE` query and rebuilt the rows, 40 to 600 ms.
- **Sorting.** Numeric and date columns hold typed values (`CellValue`: a sort key and the text shown), so they sort by value, not as text. Interval sorts new words ("-") first, then the ones in their learning steps, then by days; Memory sorts "New" first, then by recall; Next review and the Decks tab's Latest review sort by time, and the Decks tab's Words and Due as numbers. Sorting asks for a row's values many times, so they, and the collation keys of the text columns, are computed once per word and refresh.
- **Editing.** OK checks the input and saves it while the dialog is open (`Dialogs.showForm` with a check that keeps the dialog open): a missing field, an English word another word of the deck has, or a save that fails is explained under the form, which keeps everything typed, to be corrected or cancelled. Only the text columns are written (`WordRepository.updateText`), never the deck or the schedule, and the list's row is not changed; the list reads the saved word again.
- **All decks.** "All decks" lists the words of every active deck with a Deck column, a word's rows in the deck selector's order. The selected word's details name its deck, and Edit, Suspend and Delete act on the words in their own decks (Delete names the deck, or how many decks the selected words are in); the current deck stays as it is.
- **A word another deck has.** Adding a word that another active deck already has (`WordRepository.findInOtherDecks`: ignoring case, through the unique index on deck and English) asks first. The question lists each of those decks with its meaning, part of speech, phonetic and example, and offers "Copy and add", "Add as typed" or "Cancel"; it is asked before the form's meaning is required, so typing only the English word and choosing Copy is enough ("Add as typed" is then not offered). Copy puts the first deck's meaning, part of speech, example and phonetic into the form (a value that deck lacks keeps the typed one; note and tags, which are the user's own, are not copied), and the status line says where the details came from.
- **Schedules stay per deck.** Decision: a word added to a second deck is a new card there, with its own schedule. A deck is the unit of study: its new-words limit, goals, XP, badges, statistics, review sessions and JSON backup belong to that deck, and restoring a backup restores its cards' schedules. A schedule shared by the copies of a word would let a review in one deck change another deck's due count, new-word allowance and goals, and restoring one deck's backup would overwrite progress made in the other. Sharing it would need the schedule in a table of its own, keyed by the word, read by every queue, count and backup; copying the text gives the shared meaning without that. A word the user does not want to learn twice can be left out with Cancel.

## Window, Style and Accessibility

- **Size.** The window opens at 1120 x 780, or smaller when the screen's usable area is (`WindowSize`), and can be made as small as 960 x 640, never larger than the screen: a 1366 x 768 laptop offers about 1366 x 728, a 1920 x 1080 one at 150% about 1280 x 680. The Dashboard and the Review tab scroll when the window is shorter than their content (the Settings, Add / Import and Statistics tabs already did). The Review tab's rating buttons are pinned below its scrolling content, so they stay in view at any height; its result area gives up height first. In a narrow window the header's status line and the deck selector, and the Word List's search box, get narrower; buttons and labels keep their text.
- **Style.** The views give their nodes style classes and `app.css` (`AppStyle`) styles them; no view sets an inline style (`InlineStyleTest` checks the sources). Colours are looked-up colours on `.root`, font sizes are in em of the root's, so they keep their size at 100% (1em is the system's text size: 13 px on Linux and macOS, 12 px on Windows) and grow with the text size. Every text colour has a contrast of at least 4.5:1 (WCAG AA) on the window background, white fields and the cards (`AppStyleContrastTest`); the muted grey of hints and notes was darkened from #6b7280, 4.4:1 on the window background, to #5f6673, and prompt texts use it too, since the Word List's filters show only a prompt.
- **Text size.** The Settings tab's text size puts the class `text-size-115` or `text-size-130` on the window's root, which sets its font size to 1.15 or 1.3 em; every dialog (`JavaFxDialogs`) gets the stylesheet and the size saved when it opens. Sizes set in pixels (column widths, the answer field) do not grow.
- **Labels and keyboard.** Every form field has a label that names it for screen readers (`Label.setLabelFor`, through `Widgets.formLabel`); a field without a visible label (the Word List's filters, the lookup and import paths, the answer field, tables and lists) has an accessible text instead (`AccessibilityUiTest` checks every input). Form labels have mnemonics: Alt and the underlined letter moves to the field, unique among the header and one tab, or one dialog (header: Deck; Review: Mode, Session size, New words/day; Add / Import: deck, English, Chinese, Phonetic, POS, Tags, Example, Notes; Settings: retention, starts at, words per day, text size, Provider, Base URL, API key, Model, Temperature; the edit and goals dialogs label their own fields). A form dialog puts the keyboard in its first field instead of on OK. The tab order follows the layout: the Review tab's rating buttons come after its content.

## Dictionary Services

`DictionaryServiceFactory` composes the lookup chain, asked in this order until a dictionary has the word:

1. the offline dictionaries (`LocalDictionaryService`): the imported ECDICT dictionary, then the bundled GRE starter words;
2. the configured API (`HttpDictionaryService`), only when `DICTIONARY_API_BASE_URL` is set; `DICTIONARY_API_KEY` is sent as a bearer token and as `X-API-Key`, under the same rules as the AI key (see API Keys): while a key is set, a plain-http address other than this computer is not asked;
3. through the lookup cache (`CachingDictionaryService`, table `dictionary_cache`): the public online dictionaries (`PublicOnlineDictionaryService`), dictionaryapi.dev and then the English Wiktionary.

Every lookup ends with a `LookupOutcome`: `FOUND`, `NOT_FOUND`, or why the dictionary could not be asked: `NETWORK_ERROR`, `TIMEOUT`, `AUTH_ERROR` (HTTP 401/403), `RATE_LIMITED` (429), `SERVICE_ERROR` (5xx, an invalid address, or a plain-http address that would expose the key), `BAD_RESPONSE` (malformed JSON), `INTERRUPTED` or `OFFLINE` (offline mode is on). When no dictionary has the word, the chain answers `NOT_FOUND` only if every dictionary said so; otherwise it reports the first reason one of them could not be asked, and the message keeps what each one said. Verifying a word follows the same rule: `VERIFIED`, `UNVERIFIED` (every dictionary said not found) or `UNCHECKED` (one could not be asked).

Only the public online dictionaries are cached. They give English definitions only, and everything that can give a Chinese meaning answers before the cache, so an English-only entry cached earlier never hides a re-imported ECDICT or a newly configured API. A cache entry records the dictionary that answered (`source`) and when (`created_at`) and is used for 30 days; after that the word is looked up again, and while the dictionaries cannot be asked the old entry is still shown with a note. "Not found" is remembered in memory for 10 minutes, so adding a word that a lookup just missed does not ask again; a failure to ask is never remembered. "Refresh cache" asks again in any case: it replaces the entry, drops it when the dictionary no longer has the word, and keeps it when the dictionary cannot be asked. The offline dictionaries are never cached. Earlier versions did cache them; such a leftover entry (source ECDICT or the starter words) is ignored and dropped, so a raw ECDICT translation is not shown while ECDICT is being imported or after it was cleared. Earlier versions also cached the configured API's and Wiktionary's answers (source `dictionary`), read by the old parsers; such an entry is looked up again rather than used, so an old non-English or misspelling-only Wiktionary entry no longer verifies a word.

**Offline mode** ("Offline mode / 离线模式" in the window header and on the Settings tab, setting `network.offline`, off by default) skips the configured API and the public online dictionaries: `DictionaryServiceFactory` wraps both in `OfflineAwareDictionaryService`, which reads the setting at every lookup and answers `OFFLINE` without a request, so switching applies at once. The offline dictionaries still answer, and so does the lookup cache, also with an entry older than 30 days (with the note above). A word that is in neither cannot be checked: the lookup box says that offline mode is on and offers no Retry, and "Add word" offers to add it unchecked (tag `UNCHECKED`) or cancel. The header's subtitle ends with "Offline mode" while it is on.

The online dictionaries share one `HttpClient` (5 s to connect, 5 s per request) and parse their answers with Jackson. The configured API may answer with an array of entries or an object holding them in `entries`, `data`, `results` or `result`; an entry has its Chinese meaning in `chinese`, `translation` or `meaning`, an English `definition`, and senses nested in `senses`, `meanings`, `definitions` or `translations` that inherit the entry's word, phonetic and part of speech; other fields (such as `meta`) are ignored. Only Wiktionary's English section counts, so a misspelt English word that is a word in another language is not verified, nor is an entry that only says "Misspelling of ...", with or without a usage label such as "(nonstandard)"; its HTML is reduced to text. An interrupted lookup stops the chain and keeps the thread's interrupt flag.

The Add / Import tab never looks a word up on the JavaFX thread. "Lookup online" and the check behind "Add word" run through `UiAsync.start`, which returns a handle that cancels the work (interrupting its thread) and drops its result. A spinner shows while they run and the buttons stay usable: a new lookup or a change to the looked-up word cancels the running lookup, and a change to the English word cancels the check before an add; the rest of the form is read when the check finishes. A word the dictionaries do not have is added as `UNVERIFIED` only after confirmation. When they could not be asked, the add dialog offers Retry, adding the word unchecked (tag `UNCHECKED`) or Cancel, and the lookup box says why and shows a Retry button.

### ECDICT

The ECDICT CSV is imported once into its own SQLite file next to the database, `ecdict.db` (`EcdictRepository`), so `vocab.db` and its backups do not grow by the dictionary's 100+ MB and the import needs no schema migration of `vocab.db`. The CSV itself is never copied into the repository.

- `ecdict(word TEXT PRIMARY KEY COLLATE NOCASE, phonetic, definition, translation, pos, collins, oxford, tag, bnc, frq, exchange, example)` holds the rows as the CSV has them (ECDICT is unique on the word ignoring case; when a word repeats, the first row wins). `example` is only filled from word-list CSVs.
- `ecdict_forms(form, lemma, kinds)`, primary key `(form, lemma)`, comes from the `exchange` field: the `p:`, `d:`, `i:`, `3:`, `r:`, `t:` and `s:` inflections of a base form, and the `0:` base form a row that is itself an inflection names.
- `ecdict_meta` records the source path, its size and modification time, the entry and skipped-row counts, the import time, the format (encoding, delimiter, columns) and the duration. `PRAGMA user_version` is the file's format; a file of another format reads as not imported and is imported again.

`EcdictImportService` streams the CSV through the shared `CsvReader` (quoting, ECDICT's literal `\n`, byte order marks, GBK, headerless files) and `EcdictColumns` (columns by header name, or ECDICT's order for a headerless file whose fourth field is Chinese, otherwise english, chinese, pos, example, tags). It writes 5,000-row batches in one transaction into `ecdict.db.importing` (no journal and no fsync: the file is thrown away if anything goes wrong) and swaps that file in place of `ecdict.db` only when every row is in. Lookups keep answering from the previous file during an import; a failure, a cancel or a crash leaves it as it was. An import holds a file lock on `ecdict.db.import-lock`, so when the app runs twice only one window imports and a starting window never deletes the file the other one is building. Progress (rows and bytes) is reported every 10,000 rows and cancellation is checked every 1,000. A file that cannot be read fails with its line number, a header without a word or Chinese column and a file without entries are reported as such; nothing fails silently.

The ECDICT box on the Settings tab tests a file (encoding, columns and the first 200 rows; nothing is imported or saved), imports it in the background with a progress bar and a Cancel button, and saves the path only when the import succeeds. Opening the window never parses the CSV: it compares the saved path's size and modification time with `ecdict_meta` and imports in the background only when they changed or nothing is imported yet (for example after upgrading from a version that read the CSV at every start); without a saved path `ECDICT_CSV_PATH` is used. "Save and Import" skips an unchanged file, "Re-import" imports it anyway, and "Clear Dictionary Path" also deletes `ecdict.db`. The imported dictionary keeps working when the CSV is moved or deleted.

Lookups are indexed queries (`EcdictRepositoryTest` checks the query plans) that keep almost nothing in memory, and translations are cleaned as they are read (`EcdictTranslationCleaner`), so the add form gets a Chinese answer key the learner can type: ECDICT's literal `\n` separates lines, leading part-of-speech markers (`vt.`, `n.`, `adj.`, ...) become the part of speech ("verb; noun"), an inflected form's remark such as "(abandonment 的复数)" moves to the note, lines tagged `[网络]`, `[计]`, `[医]`, ... move to the note unless the word has nothing else, and the senses are joined with "; " without splitting inside brackets ("使(马,鹰等)戴头罩"). A meaning longer than 200 characters keeps its first senses and lists the rest in the note. A word that is not an entry but an inflection of one ("abandons") returns its base form, and the result says so.

### Decks from ECDICT Tags

"Create deck from ECDICT tag..." on the Decks tab (`EcdictDeckBox`, `EcdictTagDeckService`) builds a deck from the words ECDICT's `tag` field gives an exam: gre, toefl, ielts, cet4, cet6, ky (考研), gk (高考) or zk (中考). It needs an imported `ecdict.db`; without one it says where to import it. The form chooses the tag, the deck (a new name, or an active deck to fill; "GRE (ECDICT)" by default, following the tag), an optional limit and the order: most common first (ECDICT's `frq` rank, else its `bnc` rank, words without either last) or alphabetical.

- `EcdictRepository.findByTag` reads the tag's entries with one query; ECDICT has no index on its tags, and a scan of 770,000 rows takes a fraction of a second, off the JavaFX thread.
- Each word gets the meaning, part of speech and note a lookup gives (`LocalDictionaryService.toEntry`, see above), ECDICT's phonetic and the exam tag as its tag. A word whose spelling the app does not accept ("a.m.") is skipped and counted.
- Words the deck already has, suspended ones too, are skipped (compared as the deck stores them: spaces collapsed, case ignored); the limit counts the words added, so building the same deck again adds the next words. Words are inserted in the chosen order, so new cards are introduced most common first.
- The words are written in batches of 250, each in its own short transaction (the first also creates a new deck), with a progress bar and Cancel, so a rating made meanwhile waits for one batch at most (see SQLite Schema, Long writes). A cancel stops before the next batch and a failure after the batches already written; both keep them, say how many words were added, and make the deck the current deck, and building the same deck again adds the rest (the deck's words are skipped, also one added on the add form meanwhile: `WordRepository.insertAllIfAbsent`). A cancel before the first batch adds nothing, not even the deck, and a new deck that would stay empty is not created. Adding words earns no XP and counts no new words. The deck becomes the current deck.

## CSV Import and Export

Every CSV file is read and written through `service/csv`:

- `CsvReader` streams RFC 4180 records: quoted fields can hold the delimiter, doubled quotes and line breaks, and each record knows the physical line it starts on, so import messages name the line a text editor shows. It skips a byte order mark and empty lines, sniffs the delimiter (comma, tab or semicolon) from the first records, and reports a quote that is never closed with its line.
- `TextEncoding.detect` trusts a UTF-8 or UTF-16 byte order mark. Otherwise a file that is valid UTF-8 throughout is UTF-8, and anything else is read as GB18030, a superset of the GBK that Excel and Notepad on Chinese Windows write. A file whose first 16 non-ASCII characters are valid UTF-8 before a bad byte is still UTF-8 (one damaged or pasted-in character), so the import names that line instead of garbling every meaning as GB18030. Bytes that are invalid in the chosen encoding stop the read with their line number; they are never replaced.
- `WordColumns` maps columns by header name, ignoring case, spaces and underscores, with English and Chinese aliases from `WordColumn` (english/word/单词, chinese/meaning/释义, pos/词性, example/例句, phonetic/音标, note/备注, tags/标签). A first row that names at least two different fields is the header. A first row whose first cell names the English column but whose other names are unknown ("English,Meaning (中文)") is skipped as a header and the other columns are detected. A word list without a header has its columns detected from the content (see Word Lists and Anki). The local dictionary uses the same header mapping, and reads a headerless file as ECDICT's own column order only when the first row has five or more fields with Chinese in the fourth.
- `CsvWriter` writes UTF-8 with a byte order mark (without it Excel on Chinese Windows shows the Chinese garbled), CRLF line ends, and quotes only where needed. `FormulaGuard` puts an apostrophe in front of cells that start with `=`, `+`, `-`, `@`, a tab or a carriage return, so a spreadsheet does not run them as formulas; plain numbers are left alone. The importer removes exactly that apostrophe, so "Export words CSV" (whose header uses the importer's column names) followed by "Import word list" reproduces every field.

"Import word list" loads the deck's English words once for the duplicate check, turns line breaks inside a meaning cell into "; ", lists at most 100 skipped-row messages, and stops at 2,000 imported words. "Preview and map columns" also shows the encoding, delimiter and column mapping it used. Errors name the file, the line and the reason, and keep the original exception as the cause.

## Word Lists and Anki

`ImportExportService` reads every word list through `service/wordlist` (GRE CSV, TSV, Anki plain-text exports, lists of English words) and exports a deck for other apps.

- **Anki headers.** `WordListFile` reads the lines at the top that start with `#` (`AnkiHeader`): `#separator:` (tab, comma, semicolon, space, pipe, colon or the character itself), `#html:`, `#columns:`, `#tags:` (tags for every note) and the 1-based `#tags column:`, `#deck column:`, `#notetype column:` and `#guid column:`. Other `#` lines at the top (comments, `#deck:`, `#notetype:`) are skipped; messages still count them in their line numbers. The records follow through `CsvReader`, with Anki's separator or a sniffed one.
- **Fields.** With `#html:true`, or without `#html:` in a cell that holds HTML tags or entities, `HtmlText` turns `<br>`, `<div>`, `<p>` and `<li>` into "; " (a space after a line that ends in punctuation), drops `<style>` and `<script>` blocks with their text and other tags, and unescapes entities; `#html:false` keeps the text as it is. `[sound:...]` and `<img>` are dropped from every field, and an Anki cloze deletion keeps only its text (`{{c1::obdurate}}` and `{{c1::zealot::fanatic}}` become obdurate and zealot), so an example from a Cloze note reads as a sentence and the Cloze review can blank the word. A part of speech or phonetic standing alone among the meanings ("减弱；减少<br>verb") goes to its field unless the file has a column for it. Anki's space-separated tags become "; "-separated; the guid, deck and note type columns are never read.
- **Columns.** A header row decides alone (`WordColumns.fromHeader`), and so do `#columns:` names, which also know Anki's Front, Back, Text and Extra. Otherwise `ColumnDetector` reads the first 50 rows: a column is the English word, the Chinese meaning, the phonetic, the part of speech or an example sentence when at least half of its non-empty cells look like one, the first such column gets the field, and the columns left over keep a headerless GRE CSV's order (english, chinese, pos, example, tags). A single column is a list of words; its first line is a header only when it names the English column ("word"), so a list that starts with "definition" or "sentence" imports that word. A phonetic is IPA, or slashes or brackets around a stress or length mark, so a label such as "[formal]" stays in the meaning.
- **Mapping.** "Preview and map columns" (Add / Import tab, `ColumnMappingPane`) shows the encoding, separator and Anki headers, a combo box per field (English, Chinese meaning, Example, Tags, Phonetic, Part of speech, Note) listing the file's columns with their names and first values ("Column 2 · Back: 减弱"), the detected one selected, and the first 8 rows as they would be imported with what happens to each. Choosing another column previews again with those columns (`WordListOptions`), and "Import word list" uses them while the preview shows that file; a header row is skipped whatever is chosen. The choice is not remembered between files.
- **Word-only lists.** A row without a Chinese meaning (no Chinese column, or an empty cell) gets the meaning, phonetic, part of speech and, when it has none, example from the local dictionaries: the imported ECDICT in `ecdict.db` (an inflected form gets its base form's meaning, and the note says so) and then the bundled starter words; the note names the dictionary. Decision: a word they do not have is skipped and listed with the reason ("zzyzx is not in the local dictionary, so it has no meaning to import") instead of being imported `UNVERIFIED` with a placeholder, because validation requires a meaning and a placeholder would become the answer key the review grades. The online dictionaries are asked only when the user ticks "Look up meanings the local dictionary does not have online too" and offline mode is off when the import starts (the box is disabled while offline mode is on); otherwise the import service never builds the online chain, and a preview never asks online. Lookups run in the background with a progress bar and Cancel; the words are inserted in file order, in one transaction, only after every lookup, so a canceled import imports nothing. While it runs, the column choice and the online box are disabled; a word added to the deck meanwhile (on the add form) is skipped as a duplicate rather than failing the transaction on the unique index. `ImportExportService` without dictionaries skips such rows and rejects a header without a Chinese column, as before.
- **Exports** (Add / Import tab). "Export for Anki (TSV)" writes UTF-8 without a byte order mark, LF line ends, `#separator:tab`, `#html:true`, `#columns:` naming English, Chinese, Example and Tags and `#tags column:4`, then one note per word of the deck, suspended ones included as in the CSV export: the word, the meaning with the part of speech and phonetic on a second line (`<br><span class='pos'>verb</span> <span class='phonetic'>/əˈbeɪt/</span>`, which the import reads back into their fields), the example and the tags separated by spaces (a space inside a tag becomes `_`). Text is HTML-escaped and not formula-guarded. Importing the file gives the same words, meanings, parts of speech, phonetics, examples and tags (`AnkiExportRoundTripTest`); the note is not exported. "Export word list (txt)" writes the English words, suspended ones too, one per line (UTF-8, CRLF), which import again as a word-only list.

## AI / Mock Design

`AiService` is an interface. `AiServiceFactory` chooses `MockAiService` by default and switches to `OpenAiCompatibleAiService` when AI settings exist in SQLite or when `VOCABOOST_AI_BASE_URL`, `VOCABOOST_AI_API_KEY`, and `VOCABOOST_AI_MODEL` are configured (optionally `VOCABOOST_AI_TEMPERATURE`). The Settings tab can save provider, base URL, API key, model and temperature to the local `settings` table, then reload the service immediately. The services are composed as `FallbackAiService(CachingAiService(OpenAiCompatibleAiService), MockAiService)`. `CachingAiService` wraps only the real provider, so `ai_cache` holds provider responses only. `FallbackAiService` sits outside the cache and keeps review usable if the provider fails: that call shows the mock text with a failure note, nothing is cached, and the next call asks the provider again. **Test AI Explanation** calls the provider directly through `AiServiceFactory.createUncachedProvider`, without the cache or the fallback, and shows either the provider's response or its error.

- **Offline mode.** The composed service is wrapped in `OfflineAwareAiService`, which reads offline mode at every call: while it is on, explanations (and Regenerate) are the mock text with the note "Offline mode is on: no AI request was sent.", nothing is sent or cached, `isAvailable()` is false (the header shows "AI: mock" and Regenerate is hidden), and **Test AI Explanation** refuses to send. AI requests are only ever sent when a provider is configured; without one the factory returns the mock.
- **Request.** After an answer is submitted the Review tab asks for an `ExplanationRequest`: the card, the typed answer and the question's direction (English shown and Chinese typed, the reverse, or a cloze: the example with the word blanked out). The user message lists the word, its part of speech, the deck's Chinese meaning, the card's example, the direction and the learner's answer ("(left blank)" for an empty one). The system prompt asks for one JSON object with `meaning`, `answer_feedback` (whether the answer is right and, if not, what it was confused with), `memory_tip` (a mnemonic or a contrast with a confusable word), all in Chinese, and `example_en` with its translation `example_zh`.
- **Reply.** `AiExplanation` reads that JSON leniently (inside a code fence, after other text or a `<think>` block, with single quotes, trailing commas or other key names such as `mnemonic`) and shows it as labelled sections (Meaning, About your answer, Memory tip, Example). A reply that is not such JSON is shown as it is.
- **Endpoint and parameters.** `AiEndpoint` accepts a base URL or the full endpoint: a URL without a path, or whose path ends in an API version (`/v1`, `/openai/v1`, `/api/paas/v4`, `/v1beta`) or in `/openai` (Gemini's `/v1beta/openai/`), gets `/chat/completions` appended; any other path is used as given. No temperature is sent unless one (a plain number from 0 to 2, saved as such) is configured, since some models accept only their default; an invalid configured value is logged and ignored.
- **Cache.** The key is `explain:v2:<english>:<sha-256>`, where the hash covers the provider identity (`OpenAiCompatibleAiService.PROMPT_VERSION`, now 2, the temperature, base URL and model, but not the API key) and everything the prompt sends: the word's fields, the direction and the typed answer (trimmed, spaces collapsed, lower case). An explanation written for one answer is therefore never shown for another, and changing the endpoint, model, temperature or prompt requests new explanations; rows of the older prompt simply stop being used. **Regenerate explanation** on the Review tab (shown when a provider is configured) calls `AiService.regenerate`, which asks the provider again and replaces the cached row; **Clear AI cache** in the AI settings deletes every row of `ai_cache` after a confirmation.

### API Keys

The AI key (and `DICTIONARY_API_KEY`) is only ever sent in its request header:

- **Storage.** A key saved in the AI settings is stored as plain text in the `settings` table of `vocab.db`. It is deliberately not "encrypted" or obfuscated: the app would have to keep the means to decode it next to it, so anyone who can copy the file could decode it too, and obfuscation would only suggest a safety that is not there. The protection is the data folder: at startup `DataFolder` makes `~/.vocab-trainer` accessible to its owner only (POSIX 700) where the file system has POSIX permissions (Linux, macOS); on Windows nothing is changed, since the folder lies in the user's profile, which other accounts cannot open by default, and a failure is logged without stopping the app. A user who does not want the key in the database sets `VOCABOOST_AI_API_KEY` instead. Treat `vocab.db` and its snapshots (copies of it, in the data folder's `snapshots` folder) like a password file when sharing or syncing them; the JSON backup, the CSV exports and the Markdown report hold no settings and so no key.
- **Display.** The settings form never puts a saved key back on screen: the `PasswordField` stays empty and hidden, and the box shows "Saved, ends with ••••abcd" (the last four characters, or none for a key shorter than 16) with **Replace** and **Remove**. Saving with an empty key field keeps the saved key.
- **Messages and logs.** No message or log record contains the key. A key with characters an HTTP header cannot carry (a space, a line break, a full-width character from a Chinese input method) is refused before a request is built, because the JDK would quote the whole header value, key included, in its exception; a provider error that echoes the key shows `***` instead.
- **Transport.** A key is sent only over https, or over plain http to this computer (`localhost`, `127.0.0.1`, `::1`), where local servers such as Ollama listen. A plain-http base URL to any other host is refused when saving the AI settings and again before each request ("... uses plain http, which would send the API key unencrypted ..."), so nothing is sent. A request with a key never follows a redirect (the AI client never does; the configured dictionary API gets its own client for that), since the JDK passes headers such as `X-API-Key` on to the new address, even another server or plain http; a redirect ends the lookup with a message instead.

## Review Sessions

`ReviewService` owns session state: active deck, mode, current Mixed-mode question direction, target size, the cards rated so far, accuracy, XP and unlocked achievements. A card can only be rated after an answer was submitted; the submitted answer is kept until the rating is committed, so a failed save can be retried from the Review tab with the same answer and similarity.

- **Queues.** Learning and relearning cards whose step time has come go first, soonest first. Then review cards due today come from their own query, the ones most likely forgotten first (lowest R, i.e. highest elapsed time over stability), and new cards from another, in the order they were added (`added_at`, `id`), up to the deck's new-cards-per-day limit (default 20). The limit counts the deck's `LEARN` logs since the start of the study day, so it holds across sessions and restarts. The two are interleaved, one new card after every 4 review cards, but new cards wait while the due reviews alone fill the rest of the session (in an All Due session: while more than 100 are due). A bulk import therefore never hides learned words, and only the day's allowance of new words is due. When nothing is due, a learning card due within 20 minutes is shown early (Anki's learn-ahead), so a failed or new card is tested again in the same session.
- **Due counts.** The dashboard's "Due today" (and the deck table's Due column) is what an All Due session would show: "Due reviews" (learning, relearning and review cards that are due) plus "New available today" (new words the limit still allows). The Statistics tab's overdue count is the due reviews only. `ReviewQueueCounts` computes these; `WordRepository.countDueByState` splits the due words in one query.
- **Session.** A card is shown once per session; only a learning or relearning step brings it back. The target counts different cards; `0` means All Due: every due review and the new cards still allowed today. Once the target is reached, only the session's own cards still being learned come back, until none is due within the learn-ahead window. The session-size selector always shows the target: choosing a size applies to the running session at once (a session that reached its target goes on when the new one is larger), and changing the mode, Reset or a deck switch starts a new session with the same size. The size and mode the user last chose, and each deck's limit, are saved in `settings` (`review.sessionSize`, `review.mode`, `review.newCardsPerDay.<deckId>`; `ReviewSettings`), and the next launch starts with them.
- **Weak Words.** The session shows the deck's weak words, due ones first; each once, then the session ends. A due weak word is reviewed as usual. One that is not due yet is *practiced*: the log says `PRACTICE`, and the card's state, memory, counters and due date stay as they are, because FSRS learns little from an early success and would only stretch the interval. A failed practice (one that counts as Again) can only bring the due date forward, to the start of the next study day; it never moves it later and is not a lapse. Practice earns half the XP of a review and does not count towards the review goal, accuracy, streak or review achievements; replaying a word's history skips practice logs. The rating buttons of a practice show the unchanged due date.
- **Cloze / 例句填空.** The question is the card's example sentence with the word and its inflected forms blanked out (`ClozeMaker.make`, see Word Details), with the Chinese meaning and part of speech as a hint; the learner types the English word. It is graded like Chinese to English (`AnswerGrader.gradeCloze`), and the word as the sentence has it ("admonished" for admonish) counts as the word itself; the result says "Correct answer: admonish (in the sentence: admonished)". A card whose example makes no cloze (there is none, the word is not in it, or nothing but the word is left) is skipped for the rest of the session, and the session line counts it ("12 cards without examples skipped"); the queues and the new-card limit are otherwise those of the other modes. In Cloze mode the queues are read further, twice as far each time, while their head holds only cards that cannot be asked, so a deck where most cards have no example takes a few reads per card shown, not one per skipped card.
- **Directions.** Every log records the question direction. English to Chinese, Chinese to English, Cloze and Mixed (a random direction per card, English to Chinese or Chinese to English) share one schedule per card. Decision: a separate production schedule would double every word's reviews, and the GRE's verbal questions offer the words as choices, so recognising a meaning matters most; the schedule stays shared but leans on the harder skill. A failure counts fully in either direction (a production Again on a mature card is a normal lapse), while in Mixed mode an Easy on a recognition question counts as Good, so recognising a word never grows the shared interval more than a normal Good review would; its Easy button shows Good's interval. Outside Mixed mode the user chose the direction, and Easy counts as Easy. Decision for Cloze: it is a production question (the English word is typed), with more help than Chinese to English (the sentence and the meaning), and it shares the card's schedule like Mixed mode does; a separate cloze schedule would ask every word a third time. Its ratings count as they are, as Chinese to English ones do: the user chose the mode, and a cloze is never easier than recognising the word. The logged direction lets a later version split the schedules or the statistics. JSON backups carry `CLOZE` too; an older version restoring such a backup reports those logs as invalid rows and skips them.

## Goals, XP and Streak

Every daily number is read from `review_logs` with one query (`ReviewLogRepository.dailyCounts`, through `DailyReviews`), so the Dashboard, the daily goal, the Statistics charts, the session's completion summary and the Markdown report show the same numbers for a day (`DailyNumbersAgreementTest`).

- **Day.** A day is a study day: it starts at the rollover hour (`scheduler.dayRolloverHour`, 4 am by default), so a review at 1 am counts for the evening before. A `daily_goals` row is dated by study day too.
- **Reviews and accuracy.** A review is any saved rating except `PRACTICE` (a Weak Words practice of a word that was not due). Accuracy is correct reviews over reviews, by the one rule of `ReviewLog.isCorrect()` (see Answer Checking). Deleting a word deletes its logs, so its reviews leave every count at once.
- **New words.** A word counts as a new word on the study day of its first review (its `LEARN` log: state `NEW` to the first rating). Adding a word, importing a file or the starter words and restoring a backup earn no XP and count no new words.
- **XP.** A review earns 5 XP when correct (2 when not), plus the quality of the rating it counted as and up to 8 for the answer similarity; a practice earns half of that and a badge its reward. XP is stored per deck and study day (`daily_goals.xp_earned`); the Dashboard shows the deck's total.
- **Daily goal.** A deck's day is complete when its reviews reach the review goal and its new words the new-word goal; the review that completes it marks the row and unlocks the Daily Goal badge, once.
- **Streak.** One streak for the user, not per deck: the study days in a row with a review in any deck, practice not included. A day still in progress does not break it. It is read with one query whatever its length: a recursive query steps back one study day at a time inside SQLite, each step one indexed lookup of the newest review before that day started (`ReviewLogRepository.reviewDaysBackFrom`), and it stops at once when the newest review is older than yesterday, since no run can reach today from there. A rating computes the progress, streak included, once: the goal update returns it and the badges' XP is added to it without reading it again (`GoalServiceTest` counts the statements at a 400-day streak).
- **Badges.** First Review and 10, 50 and 100 Reviews count the deck's reviews in its logs (counting stops at 100); Daily Goal and Overdue Rescue belong to the deck. The streak badges (3, 7 and 30 days) belong to no deck and show in every deck. One that an older version unlocked in a deck stays in that deck's rows, shows in every deck too and is not unlocked or rewarded again. A deck's JSON backup carries the streak badges the deck shows; restoring it adds one for no deck unless the database has it already, so it is not unlocked again with its XP.
- **Goals.** `GoalSettings` keeps the goals in `settings`: the default review and new-word goals of every deck (`goals.reviewsPerDay`, `goals.newWordsPerDay`; 20 and 5 until changed), a deck's own goals (the same keys followed by `.<deckId>`) and the session goal, which is the review session size of every deck (`review.sessionSize`, see Review Sessions). The session size has no per-deck value, so a deck switch keeps the size the user chose. The Dashboard's "Edit goals" form (`Dialogs.showForm`, also opened from the Settings tab) edits the goals of every deck or of the current deck only and publishes `GOALS`, on which the Review tab takes the new session size at once. Today always has the current goals; a past day shows the goals stored in its row. The form reminds the user that the deck's new-cards-per-day limit caps the new words of a day.
- **Older data.** Past rows keep their counters, XP and completion, including the XP older versions gave for imported words, and their calendar dates. Logs written before schema version 6 read as reviews, so those days count no new words.

## Undo, Suspend and Already Known

Mistakes on the Review tab and in the Word List can be taken back.

- **Undo.** `ReviewService` keeps what the session did as a stack (`UndoAction`): each rating, each new card marked as already known and each card suspended from the Review tab, at most 100, the latest first. Starting a new session (a deck switch, a mode change, Reset or Start Session) empties it. `undoLast` takes back the latest action in one transaction: the card gets back its review state exactly as it was (FSRS state, stability, difficulty, learning step, due and last review times, counters and the SM-2 fields, and not suspended), and its tags as they were unless they were edited since (so the `leech` tag a rating added goes, while a tag the user typed since stays; the text fields are never touched); the action's review log is deleted; `GoalService.revertReview` subtracts the rating's counters and XP (its own and its badges') from the study day it was saved on, clears the daily goal's completion when that rating completed it and deletes a `daily_goals` row left without progress; `AchievementService.revoke` deletes the badges it unlocked. The day's numbers, the streak and the new-word allowance are read from the logs, so they follow. The session's count, accuracy, XP and badges go back too. A card deleted since cannot be restored: undoing its action reports that and drops it, so the action before can be undone next.
- **On screen.** Decision: an undone rating brings its card back answered: the typed answer, the check, the interval previews and the explanation, with the suggested rating focused, since the usual mistake is a misclicked rating rather than a wrong answer; rating it again logs the original answer and response time. A card marked as known or suspended comes back with its checked answer if it had one, otherwise waiting for its answer. A leech suspended from the leech notice while another card was shown is only unsuspended, and its notice comes back. The Undo button's tooltip says what it takes back; Ctrl+Z (Cmd+Z on a Mac) does the same while the Review tab is shown, unless the focus is in a field with text, whose own typing it then undoes.
- **Suspend / 暂停.** `words.archived`, which no earlier version ever set, means suspended (`WordCard.isSuspended`): no schema change was needed, the JSON backup already carries the flag (`archived`), and an older version simply hides suspended words. Every review queue and count filters `archived = 0`: the session queues, due counts (Dashboard, deck table, Statistics), new-card counts, the weak list, the mastered count, the hardest words and the memory chart; `WordCard.isDue`, `isWeak` and `isMastered` are false for a suspended card, and `WordPredicateAgreementTest` runs every case also as a suspended word. Suspended words stay in the Word List (Status "Suspended" and a Suspended filter; the Leech filter still lists them), the deck's word count (the Dashboard shows "215 (3 suspended)"), JSON backups and the CSV export, and `WordRepository.findByEnglish` finds them, so adding a word that is suspended says it exists instead of failing on the unique index. A card is suspended from the Review tab (the card on screen), the Word List (Suspend and Unsuspend act on every selected word; Shift- or Ctrl-click selects several), the delete confirmation and the leech notice; it is unsuspended in the Word List.
- **Delete.** The Word List deletes the selected words after a confirmation that says how many reviews go with them (and so leave the daily counts and statistics), that only restoring a JSON backup or a database snapshot made before brings them back, and offers "Suspend instead" unless every selected word is suspended already.
- **Already known / 已掌握.** A new card can be marked as known instead of learned (`ReviewService.markKnown`, refused for any other card). `CardScheduler.markKnown` puts it straight into review with a stability of 60 days (`ReviewScheduler.KNOWN_STABILITY_DAYS`), the difficulty of a first Easy rating and the interval that stability gives at the desired retention, with fuzz (55 to 65 days at 0.9); its last review time is now and its review counters stay 0. A `KNOWN` review log records it (rating Easy, similarity 1, no direction). It is not a review: `ReviewLogRepository.IS_REVIEW` leaves it out of every daily number, the goals, accuracy, the streak and the review badges, it earns no XP, it is not a `LEARN` log so it uses none of the day's new-word allowance, the hardest words and the decks' last review ignore it, and the session does not count it. Replaying a word's history applies it as `markKnown` did. An older version reads a `KNOWN` log as a review, and reports it as an invalid row when it restores a backup that has one.
- **Leech notice (A12).** When a rating makes a card a leech, a notice under the result names it and offers Suspend and, when an AI provider may be used (one is configured and offline mode is off), "Get a mnemonic": an `ExplanationRequest.memoryAid` (`Focus.MEMORY_AID`), whose prompt makes the memory tip the heart of the reply. It is cached under its own key; the keys of plain explanations are those of earlier versions. The memory aid is shown under the notice, which stays until the next rating, an undo, a reset or a deck switch. All of this lives in `ReviewSessionPresenter`, without JavaFX, and `ReviewView` only renders it.

## Exam Planning

`ExamSettings` keeps the exam in `settings`: every deck's (`exam.date`, an ISO date, and `exam.name`, "GRE" when none is saved) and a deck's own (`exam.date.<deckId>`, `exam.name.<deckId>`), which wins. "Set exam date" on the Dashboard or the Settings tab (`ExamDialog.open`) edits either, like "Edit goals": saving every deck's exam drops the current deck's own, and an empty date removes the exam (for the deck only: it has every deck's exam again). A saved date that is not a date is logged and ignored. Days are study days. `ExamPlanService` holds the planning; it has no JavaFX dependency.

- **Countdown.** The Dashboard's exam box (`ExamPlanBox`, right of the counts) shows "GRE in 45 days", "GRE is tomorrow", "GRE is today" or "GRE was 3 days ago", the date and whether it is the deck's own exam; an exam that is over asks for the next date, and nothing else depends on it any more.
- **Reviews before the exam.** `ReviewScheduler` reads the deck's exam date at every rating and rating preview (`ReviewScheduler.ExamDates`, wired to `ExamSettings` by `AppServices`; replaying old review logs ignores it). `CardScheduler.outcomes(card, now, examDay)` takes the FSRS outcome and, when a review interval would reach the exam day (due on it or later), shortens it with `ExamClamp`: the card is due a *lead* of days before the exam, a tenth of the interval FSRS chose, from 1 to 7 days, minus up to 3 days chosen by the card's fuzz, so long intervals spread over the final week instead of all falling on one day. When today is already within the card's lead, today's review is its last one and the interval stays (an exam tomorrow changes nothing); an exam today or over changes nothing. Only the due date and the interval move: stability and difficulty are what FSRS computed (`Fsrs` is untouched), and the earlier review is an ordinary FSRS review of an early card. Hard, Good and Easy then never give a shorter interval than the rating below them (a clamped Good takes Hard's later day). The rating buttons show the shortened interval followed by "(exam)", for example "Good (3) · 16d (exam)". A new word marked as already known (`CardScheduler.markKnown`) is clamped the same way, so its two months of stability do not carry it past the exam. So every card that would reach the exam gets a review in the last 7 days before it; `ExamClampTest` checks this for every interval and distance.
- **Cards already scheduled after the exam.** Saving an exam date brings forward, in the same transaction, every active review card due on or after its deck's exam day that was not last reviewed within its lead of it: it becomes due on its lead day before the exam, or today when that day has passed (`CardScheduler.dueBeforeExam`). The Dashboard says how many. The same pass runs at every start and after a JSON backup restore (`ExamPlanService.bringReviewsBeforeExams`), for reviews that a restore or the card-state backfill scheduled after the exam; it reads only cards due on or after the first exam day ahead (`ExamSettings.firstExamAfter`), so without an exam it reads none. Moving the exam later or removing it moves no card back; an early review costs FSRS little. A checked answer's rating buttons are previewed again when the exam date changes.
- **New-word plan.** `NewCardPlan` is the smallest new-cards-per-day limit with which every new word of the deck (never reviewed) is introduced before the exam: today lets in what is left of the limit after today's new words, every later day before the exam day the whole limit. The box says "To finish 1,240 new words before the exam you need ~28 new words/day (now 20)." and, when the deck's limit is lower, "Use 28 new words/day" sets it (`review.newCardsPerDay.<deckId>`, at most 9999); the Review tab takes the new limit at once (`REVIEW_SETTINGS`). There is no plan once the exam is today or over.

## Workload Forecast

The Statistics tab starts with the workload forecast (`WorkloadForecastChart`, "Next 14 days" or "Next 30 days"): for each study day from today, the reviews already scheduled (blue) and the new words planned (orange), stacked. `StatsService.workloadForecast` reads the reviews with one query, `WordRepository.countDueByStudyDay`, which groups the deck's active learning, relearning and review cards by `MAX(date(next_review_at, '-<rollover> hours'), today)`: the rollover hour decides the study day, overdue cards count for today, and so does a learning step due later today (so today can be more than the Dashboard's "Due reviews", which counts the steps whose time has come). New words follow the deck's new-cards-per-day limit: today what is left of it, then the whole limit each day until no new word is left. The reviews that new words and the coming reviews will add are not forecast. The exam day is marked on the axis ("11/16 GRE"), and the line under the chart sums the range and names the busiest day and the exam. `WorkloadForecastTest` compares the counts with counting every word one by one, for rollover hours 0, 4 and 23.
